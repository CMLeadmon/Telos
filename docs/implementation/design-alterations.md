# Standalone beta: design alterations

Every deliberate departure from the plans, with the reason, the files that carry it and
how to reverse it. Authorized by the project owner on 2026-10-13 ("make do with what you
have; progress is more important than strict adherence; inform me of the design alterations
after implementation"). Newest last.

| # | Alteration | Why | Where | Reverse by |
|---|---|---|---|---|
| A1 | The **verified reference release is Ubuntu 26.04 LTS**; the policy floor stays 24.04. The preflight labels every other release "not yet a verified combination". | The only Podman-capable environment available was a 26.04 VM; its archive ships Podman 5.7.0, so a Podman 5 source became *verified* there, whereas none exists for 24.04. | `cli/lib/preflight.sh` (`TELOS_UBUNTU_REFERENCE`), `scripts/lib/clean_install_drill.py`, `documentation/product/platform-scope.md` (amendment), `install.md`, `clean-install-evidence.md`, tests | Set the constant back and re-run the live checks on 24.04 once a Podman 5 source is verified |
| A2 | Podman-dependent gates run on a **user-space KVM VM** (QEMU extracted from apt `.deb` files, signed Ubuntu cloud image) instead of a bare-metal clean host. Evidence from it is a labeled VM-hosted rehearsal, never candidate evidence. | No sudo on the host; `/dev/kvm` was ACL-accessible. | `~/.local/telos-vm/` (outside the repository) | n/a — replace with a real host |
| A3 | Every image reference is **fully qualified** (`docker.io/...`) in both Dockerfiles and the Compose files. | Found on the real VM: a clean Ubuntu host defines no unqualified-search registries, so Podman refused `nginxinc/nginx-unprivileged` (and would refuse `clamav/clamav`, `jellyfin/jellyfin`, `grimmory/grimmory`). Docker-style short names are not portable to Podman. | `frontend/Dockerfile`, `backend/Dockerfile`, `docker-compose.yml`, `docker-compose.test.yml`, hardening test | Restore short names only if a registries.conf is provisioned |
| A4 | The `telos-client` tmpfs mounts use `mode=1777` instead of `uid=101,gid=101,mode=0750`. | Found on the real VM: Podman 5.7 (rootful and rootless) rejects `uid=`/`gid=` tmpfs options that Docker accepts. The tmpfs is private to a single non-root, read-only container, so a sticky world-writable mode grants no one else access. | `docker-compose.yml`, `tests/operations/static_client_test.sh`, `scripts/verify-frozen-artifact.py` | Use `--mount type=tmpfs` with a podman-supported ownership option once one exists |
| A5 | Bearer `POST /api/v1/auth/logout` now **revokes the caller's device** (sessions, refresh tokens, live sockets); previously it answered 400 "No active session" to any client without a cookie. `UserContext.SessionHash` is no longer serialized by `/auth/me`. | Found while writing the native logout test: a signed-out desktop client left a working credential behind, and `/auth/me` returned the session lookup hash to the member. The plan's table specified "`/auth/logout` with bearer" without changing the handler. | `backend/main.go`, `backend/devices_integration_test.go` | Revert the handler branch (clients then must `DELETE /users/me/devices/{id}`) |
| A6 | Phase 3 Tasks 2, 3 and 4 landed in **one frontend commit** rather than three. | The TypeScript auth lifecycle, the credential bridge and the TLS removal share types and tests; intermediate states would not compile (the plan itself notes this ordering problem). All three tasks' checks were run on the combined tree. | commit "desktop: ..." | n/a |
| A7 | The retired plaintext store is deleted at launch and **startup aborts** if it cannot be removed safely (symlink, directory, permission failure). | "Surface removal failures": leaving a plaintext refresh token on disk is worse than refusing to start. | `frontend/src-tauri/src/lib.rs`, `credentials.rs` | Log and continue instead of returning the setup error |
| A8 | Media URLs are **minted for both browser and desktop clients** (`playback-locator`, `stream-ticket`), not only for token mode; the legacy authenticated `GET /api/v1/stream/video/{id}` redirect and `/audio/{id}` routes remain for API compatibility but the UI no longer uses them. | One code path means the browser exercises the same revocable capability the desktop depends on. | `frontend/src/components/stream/HlsPlayer.tsx`, `backend/streamticket.go`, `backend/routes.go` | n/a |
| A9 | The PDF reader in token mode loads the **whole document through the authenticated client** and hands PDF.js bytes (no range requests); the browser keeps streaming. | PDF.js's own requests would carry an access token captured once and expired mid-read; there is no hook to refresh it. | `frontend/src/components/library/PdfReader.tsx` | Add a PDF.js transport that calls the refresher before each range |
| A10 | In token mode the audiobook **Media Session artwork is omitted**. | The OS fetches artwork outside the document, where a token-mode client cannot authenticate; a blob URL is not guaranteed to be honoured. | `frontend/src/components/library/AudiobookPlayer.tsx` | Provide a signed cover capability |
| A11 | Capability responses force `Cache-Control: no-store` and `Referrer-Policy: no-referrer` by wrapping the response writer, overriding the upstream `Cache-Control` the media proxy would otherwise relay. | The URL is a credential. | `backend/media_authority.go` | n/a |
| A12 | `release/images.lock` is **schema version 2** with real digests resolved through `skopeo` on the reference VM; Jellyfin, ClamAV and Grimmory move from `latest` to the version tags `10.11.11`, `1.5.4` and `v3.5.0`, and the egress proxy from `ubuntu/squid:latest` to `6.6-24.04_edge` (Squid 6.14; the 7.2-26.04 build is a minimal image without the shell utilities the entrypoint needs; Squid publishes no stable version tag). The test toolchain images (`golang`, `postgres`, `redis`) come from the lock's `testImages` section. | The lock held fabricated digests (`1111…`) and omitted most services; `latest` cannot be reviewed. The versions are the newest stable tags at resolution time and were **not** exercised against the Telos integrations before pinning — the first live run on the VM is their test. | `release/images.lock`, `release/images-lock.schema.json`, `scripts/{refresh,verify}-image-lock.py`, Dockerfiles, Compose, `scripts/test-backend.sh` | Re-run `refresh-image-lock.py` for a key and commit the reviewed diff |
| A13 | **Guided setup publishes through a relay container, not through Jellyfin/Grimmory.** `docker-compose.setup.yml` now adds `telos-setup-proxy` (the gateway image running `telos-core setup-proxy`, with two fixed target pairs, on `telos-backend` plus an ordinary `telos-setup` network), and the upstream services publish nothing. Setup containers are removed by name through the runtime (`podman rm -f --ignore`), not by `compose rm`. | Found on the real VM: a container attached only to `internal: true` networks cannot have a published port (the runtime reserves the host port but installs no forwarding), so the original loopback bindings never worked; and podman-compose 1.6.0 has no `rm` subcommand, so teardown silently left the ports open. | `docker-compose.setup.yml`, `backend/setup_proxy.go`, `cli/commands/configure.sh`, `scripts/validate-compose.sh` | Give the upstream services a non-internal network during setup (this would let them reach the Internet directly) |
| A14 | **Opt-in private-CA TLS** (`TELOS_PRIVATE_CA=1`, `TELOS_TLS_PATH`): `docker-compose.private-ca.yml` and `config/private-ca/tls.yaml` serve a certificate from an operator-managed CA and point ACME at an unreachable directory. The CLI layers the overlay automatically. | The reference VMs have no public DNS name, and platform-trusted HTTPS from a private CA is a documented supported path. The rehearsal CA is minted by `tests/rehearsal/make-private-ca.sh` and installed in the verifier's OS trust store; nothing in a client waives validation. | `docker-compose.private-ca.yml`, `config/private-ca/tls.yaml`, `cli/lib/common.sh`, `cli/lib/node_config.py`, `.env.example` | Remove the overlay and the two settings |
| A15 | `cli/lib/common.sh` no longer passes `--project-directory` to Compose. | podman-compose 1.6.0 rejects the option (it is a docker-compose flag the earlier Compose double accepted); the project directory is already the directory of the first `-f` file. | `cli/lib/common.sh`, `tests/operations/{node_config,configure_integrations}_test.sh` | n/a |
| A16 | The **PostgreSQL and MariaDB services start as their own unprivileged users and do not set `no-new-privileges`** (a policy exception with compensating controls, expiring 2027-04-30); every other service keeps it. AppArmor confinement, the read-only data layout and the internal-only network are unchanged. | Found on the real VM: on Ubuntu 26.04 (AppArmor 5.0, crun 1.21's name-only `crun` profile stacked under Podman's `containers-default`) `no-new-privileges` leaves a container's processes carrying different AppArmor labels, and AppArmor then denies signals between them (`sh: can't kill pid 2: Permission denied`). The image's `gosu` step spins at 100% CPU, `pg_ctl stop` gets EPERM, and the startup process cannot signal the postmaster, so the database never starts. Postgres is the only service that signals between its own processes this way. The clean fix is host-side (stop attaching the `crun` profile), which I did not apply because it weakens the host's AppArmor configuration and that is your decision. | `docker-compose.yml` (postgres service) | Add `security_opt: [no-new-privileges:true]` back once the host no longer stacks the `crun` profile (`/etc/apparmor.d/disable/crun`) or the profile/Podman fix lands, then re-run `telos start` |
| A17 | **`telos configure integrations` now saves Jellyfin's Base URL (`/jellyfin`)** in its final validation (`telos-core validate-integrations --set-jellyfin-base-url`), after the API key has listed the libraries; it recognises a Jellyfin that already serves there and reports `jellyfin_restart_pending` for one that was saved but not restarted. | Found on the real VM: the gateway has always reached Jellyfin at `http://jellyfin:8096/jellyfin` (and its HLS rewriting requires that prefix), but a fresh Jellyfin serves from `/` and nothing in the install or setup path ever set the Base URL, so a node set up exactly as documented reported Jellyfin `degraded` and could not stream. | `backend/integration_config.go`, `backend/integration_config_test.go`, `documentation/operations/guided-integrations.md` | Make the gateway's Jellyfin base configurable (`JELLYFIN_URL`) and rewrite HLS against that path instead |
| A18 | **Jellyfin item authorization also matches a library by directory.** An ancestor whose path is one of a library's configured locations (from `GET /Library/VirtualFolders`, cached for a minute, last good map kept) counts as that library's ID. Empty media listings are no longer cached. | Found on the real VM against the pinned Jellyfin 10.11.11: `/Items/{id}/Ancestors` returns only the physical folder chain, never the library itself, so the gateway's "an ancestor is an allowed library ID" test authorized nothing and Stream showed an empty catalog. The old rule still works for servers that list the library. | `backend/media.go`, `backend/jellyfin_resolver_test.go`, `backend/main.go` | Pin a Jellyfin whose ancestors include the library, or resolve the library through `Items?ParentId` instead |
| A19 | **Grimmory's JVM is started directly as the node's app identity**, bypassing the image's root entrypoint (`entrypoint: ["java", …]` in `docker-compose.yml`), so the container never has root, a writable root filesystem or capabilities. Its data volume is created with `APP_UID:APP_GID` ownership and `telos start` repairs an older volume's owner. | The upstream entrypoint creates a user in `/etc/passwd`, `chown`s mounts and `su-exec`s, which needs a writable root and three capabilities. The plan asks for the publisher-supported identity where initialization allows it; here the same JVM command works unprivileged on an empty volume (verified on the VM, healthy in 21 s). | `docker-compose.yml`, `cli/lib/common.sh` (`prepare_volume_ownership`), `config/runtime-hardening.json` | Remove the `entrypoint`, `user` and `read_only`, add `CHOWN`, `SETUID`, `SETGID` capabilities and a policy exception |
| A20 | The installer's **minimum host is 4 CPU cores, 16 GiB of memory and 20 GiB of free shared storage**, with `TELOS_ALLOW_UNDERSIZED_HOST=1` turning the failure into a warning. The override is set only on the 12 GiB reference VM; the installer never sets it. | The plan requires the minimum; the only Podman host available has 12 GiB. The resource limits in the policy sum to about 14 GiB, so the strict default is right for a product node. | `cli/lib/preflight.sh`, `tests/operations/install_test.sh` | Delete the override and run the rehearsal on a 16 GiB host |
| A21 | The **private-CA overlay now mounts its own static Traefik configuration** (`config/private-ca/traefik.yaml`, identical except the ACME directory is unreachable) instead of an environment variable, and requires the certificate directory and key to be readable by UID 65532 (key mode 0640 group 65532 is accepted; 0600 root-only is not). | Found on the VM: Traefik ignores `TRAEFIK_*` environment variables once a static file exists, so the A14 override never worked and the node contacted Let's Encrypt for a name it could not validate. Running Traefik unprivileged then also needs read access to the key. | `config/private-ca/traefik.yaml`, `docker-compose.private-ca.yml`, `cli/lib/{common.sh,node_config.py}`, `tests/operations/private_ca_config_test.sh` | Run Traefik as root again and restore the 0600 rule |
| A22 | The **backup systemd unit does not set `NoNewPrivileges` or `PrivateTmp`**, and restarts the writers it stopped through a transient `systemd-run --scope`. | Found on the real VM: under the unit's confinement on 26.04 AppArmor swallows the signals Podman sends and breaks the network-namespace cleanup, so a backup left the stack half-stopped; and `conmon` for a container started inside a one-shot unit lives in the unit's cgroup, so the services died when the unit ended. The unit still runs as root only for the minutes it needs, holds no listening socket and reads its credentials from root-owned 0600 files. | `deploy/systemd/telos-backup.service`, `scripts/backup.sh`, `tests/operations/backup_restore_test.sh` | Add the two options back once the AppArmor stacking in A16 is gone, and keep the scope for restarts |
| A23 | **A database restore runs as the PostgreSQL superuser and the dump keeps object ownership.** `pg_dump` no longer uses `--no-owner`; `pg_restore --clean --if-exists` no longer uses `--no-owner --role=telos_owner`. | Found by the first live separate-host restore: restoring as `telos_owner` could not drop the `pg_stat_statements` extension the init scripts create (owned by the superuser), so the restore aborted. Restoring as the superuser into an initialised cluster replays ownership, grants and the extension exactly; `tests/operations/postgres_restore_roles_test.sh` proves it on two real PostgreSQL 16 clusters (ownership, the runtime/owner role split, the extension, data). | `scripts/backup.sh`, `scripts/restore.sh`, `tests/operations/postgres_restore_roles_test.sh` | Restore with `--role=telos_owner` and skip extension entries with a `pg_restore -L` list |
| A24 | **One exclusion list, `config/release-exclude.txt`, for the installer and the backup's release capsule**; a capsule over 1 GiB aborts the backup. | Found by the first live backup: `install.sh` had copied a 11 GB Rust `target/` build directory into `/opt/telos`, and every backup archived all of it. | `config/release-exclude.txt`, `install.sh`, `scripts/backup.sh`, `tests/operations/backup_restore_test.sh` | Inline the patterns again |
| A25 | **A rehearsal recovery drill may use the machine that made the backup as its observer** (`--rehearsal-source-verifier`); a candidate drill may not. Only two VMs exist, so no third machine could watch the restored host; the observation file records `verifierIsSource` and the result reason says so. A rehearsal is never certification evidence. | The gate requires the observer to be neither the source nor the restored host. The reference environment cannot host a third machine (memory) and the host cannot reach the VMs' private link. | `scripts/lib/recovery_drill.py`, `tests/operations/recovery_drill_test.py` | Run the drill from a third machine; nothing else changes |
| A26 | The recovery drill **judges the member journey without its dependency-outage stages** (`outage.*` rows that did not run are left out of the verdict, and any other unrun row makes the gate `not_run`). | Those stages stop Jellyfin and Grimmory on the host through a controller; a recovery drill only observes. The outage behaviour itself is covered by the hosted-browser journey. | `scripts/lib/recovery_drill.py` | Run the journey with a stage controller during the drill |
| A27 | The capacity load test is **one scenario of exactly 25 VUs** (`member_journeys`) that does both the reads and the paced writes (one durable write every 2.5 s per VU = 10 per second in total), instead of the plan's two scenarios (25 constant VUs plus a 10/s arrival-rate scenario). | The plan also requires "exactly 25 distinct simultaneously authenticated sessions, shared by both scenarios". k6 gives every VU of every scenario its own cookie jar, so two scenarios cannot share sessions without 25 more sign-ins. Rotating the 100 accounts through the 25 sessions (four phases) keeps "all 100 accounts take a turn". | `tests/load/telos.js` | Add an arrival-rate scenario that signs in its own writers (and accept 50 live sessions) |
| A28 | **Redis runs with `--maxmemory 384mb --maxmemory-policy volatile-lru`** (limit 512m). The gateway exports pool and stream saturation gauges (`telos_db_pool_*`, `telos_active_streams`, `telos_stream_capacity_max`). | The capacity criteria name Redis at "its configured maxmemory" and the pool/stream limits; none of the three was configured or observable. `volatile-lru` evicts only keys that expire (cache, rate-limit, presence), never one that does not. | `docker-compose.yml`, `backend/metrics.go` | Drop the two flags and the gauges; the capacity drill then reports `capacity.saturation` as `not_run` |
| A29 | The capacity target declares **at least 25 source addresses on the load host** (`sourceAddresses`); the fixture and k6 (`--local-ips`) spread sign-ins across them. | The edge allows 10 sign-ins a minute per client address; 100 members and 4 phases of 25 sign-ins cannot come from one address. (Before this, the limiter was one bucket for everybody — fixed, see the ledger.) | `scripts/lib/capacity_drill.py`, `scripts/prepare-capacity-fixture.py`, `tests/load/telos.js` | Raise the edge limit for the load host (weakens the real control) |
| A30 | **Every request the gateway sends to Jellyfin takes a start slot** (six at once; audio direct-stream starts one at a time), held only until the response headers arrive. | Found by the capacity drill and reproduced against Jellyfin 10.11.11 directly: 25 concurrent library or PlaybackInfo/audio requests make it crash with SIGSEGV after a file-lock error on its transcode directory; 12 at once is fine. The gate sits in the shared transport so no code path bypasses it; it cut the crash rate sharply but **did not eliminate it**. The real cause was found later and is A33 (`no-new-privileges` under Ubuntu 26.04's AppArmor); the gate is kept as defence in depth against overloading Jellyfin, not as the crash fix. | `backend/proxy.go`, `backend/capacity.go`, `backend/main.go` | Remove `gatedTransport` from `upstreamHTTPClient`; pin another Jellyfin |
| A31 | A **rehearsal run of a runtime-kind gate** (`capacity`, `controlled-egress`) on a node without an installed-generation receipt, or with locally built images, records every observation but ends `not_run` (`subject.runtime`), never `passed`. | A runtime subject binds the generation receipt and each service's registry manifest digest; a node installed with `install.sh` and built images has neither. | `scripts/lib/drill_common.py` (`build_runtime_subject`) | Install the node from a generation (Phase 5 builder) |
| A32 | Controlled-egress probes **join a service's network namespace by path** (`--network ns:/proc/<pid>/ns/net`), not by `--network container:`. | podman-compose puts the containers in a pod, and Podman refuses `container:` to a pod member. A joined namespace has no resolver of its own, so hostnames are pinned with `--resolve`. | `scripts/lib/egress_drill.py` | n/a |
| A33 | **Jellyfin also runs without `no-new-privileges`** (the A16 exception, same compensating controls, same 2027-04-30 expiry). The gateway's Jellyfin start gate (A30) stays as defence in depth but was **not** the fix. | Found by running the 30-minute capacity drill: Jellyfin died with SIGSEGV (exit 139) about once every 5-30 minutes under load and the drill failed on stability, latency and semantics. I first blamed Jellyfin 10.11.11 and added the start gate, which reduced but did not remove the crashes. A differential test on the reference VM then settled it: the same Jellyfin image on a copy of the real config under the same 24-way direct load, changing one container option at a time — read-only root, dropped capabilities, memory/CPU/PID limits and jemalloc made no difference (0 restarts); `no-new-privileges` alone produced 49 restarts in 100 s; the unhardened container served 144,000 requests with none. It is the A16 mechanism: on Ubuntu 26.04 `no-new-privileges` leaves the container's threads under different AppArmor labels and AppArmor denies the signals the .NET runtime sends between its own threads. | `docker-compose.yml` (jellyfin), `config/runtime-hardening.json` | Add `security_opt: [no-new-privileges:true]` back with A16 once the host stacking is fixed; re-run the 30-minute capacity drill and the direct-load differential before accepting it |
| A34 | **A product defect, not a design change:** the gateway no longer cancels a Jellyfin API request's deadline context when the helper that issued it returns; the context now lives until the caller closes the response body. | Found by the 30-minute capacity drill after A33 made Jellyfin stable: about 1 in 150 playback-info requests answered 500 with `context canceled`. `jellyfinGET` deferred `cancel()`, so a body that had not arrived when the headers did was cut off by the caller's later read. A regression test reproduces it deterministically (headers first, body 150 ms later). The 500 now also logs its cause. | `backend/jellyfin_catalog.go`, `backend/media_handlers.go`, `backend/proxy_test.go` | Revert the `cancelOnClose` wrapper (the old behaviour is the defect) |
